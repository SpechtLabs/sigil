# alertrouter policies

The Sigil documents alertrouter evaluates, laid out the way a policy
repository shared by a platform team and product teams would be. There is one
kind, `AlertRouting`: for each firing alert it decides whether to `page`
someone, `drop` the alert, or `notify` a channel.

## Layout

| Path | Owner | What it holds |
| --- | --- | --- |
| `alert_routing.sigil` | generated | The `AlertRouting` kind file, exported from `src/lib/routing/kind.ts`. Regenerate it with `bun run export-kind`; `bun test` fails when it's stale |
| `platform/alerts.sigil` | platform | `platform.alerts`: the shared `let` `pre_production`, true for an alert labelled `env: staging` or `env: dev` |
| `platform/paging.sigil` | platform | `platform.paging`: a critical alert outside pre-production, or such a warning that fires longer than `page_after`, pages the team's on-call. Every team is required to invoke it |
| `platform/routing.sigil` | platform | `platform.routing`: warnings outside pre-production notify the team channel, and pre-production alerts and alerts named in `muted` are dropped |
| `teams/<team>/alerts.sigil` | each team | `<team>.alerts`: the policy alertrouter evaluates for that team's alerts |
| `teams/<team>/alerts_test.yaml` | each team | Test cases for that policy, one per rule it can reach |
| `sigil.yaml` | platform | The paging `sigil check` requires, and its lint levels |

The platform documents are trusted. alertrouter compiles them into the app
(`src/lib/embedded.ts`, generated by `bun run embed`) and passes them to the
engine as the trusted files, apart from the team bundle, requiring
`platform.paging` in every team policy. A team can't drop the paging, gate
it, redefine it or pass it a `page_after` out of bounds: the bundle fails to
load, and a reload keeps the bundle that served before. The team documents
are the untrusted bundle. alertrouter reads them from `ALERTROUTER_POLICIES`
(a mounted ConfigMap in a cluster, `./policies/teams` in the compose stack)
and falls back to the copy compiled into the app when it's empty.

Only an alert labelled as pre-production is dropped for its environment. An
alert without an `env` label, or with one the platform doesn't know, such as
`env: prod`, pages and notifies like a production alert: a mislabelled
production alert fails loud rather than silent.

A team tunes the platform's policies through their params: `platform.paging`'s
`page_after`, how long a warning fires before it pages (30m by default,
between 5m and 1h), and `platform.routing`'s `muted`, the alert names it
doesn't want to hear about. The bounds are the platform's: a team that passes
`page_after: 2h` doesn't load. Muting drops the notification, but never a
page: `page` outranks `drop`, so a muted alert that is critical, or a muted
warning that keeps firing, still pages.

When a team's policy fails for an alert (a conflict, a failed assert, a
runtime error, an evaluation past its timeout), alertrouter evaluates
`platform.paging` on its own for the same alert, with its params at the
platform's defaults, and pages when it pages. So a broken team policy can't
turn a critical page into a channel post; a sustained warning then pages
after the platform's 30m, not the team's `page_after`.

A team adds `notify` rules of its own, to post some alerts in another channel,
and never `page` rules. Two rules of the same decision and reason with
different payloads are a conflict, and an evaluation that ends in a conflict
fails. A team page for a critical or sustained alert would tie with
`platform.paging`'s, and a team notify for a warning would tie with
`platform.routing`'s; that's why both teams' notify rules only take `info`
alerts, which no platform rule routes.

## Checks

CI runs these from `examples/alert-routing/`, through `mise run policies`. The
kind has no host functions, so the stock `sigil` binary checks and tests the
policies; the same commands work locally.

```sh
# Type-check every policy with the platform's documents as the trusted
# source, and fail if a team policy doesn't invoke platform.paging at the top
# level, as sigil.yaml requires. This is the check the service makes when it
# loads the bundle.
sigil check --config policies/sigil.yaml policies

# Run every test file.
sigil test -v policies

# From policies/, sigil.yaml is found without --config, and its kinds: and
# trusted: paths let a command work on one team's directory.
cd policies && sigil check teams/payments && sigil test teams/payments

# Formatting; the root `mise run sigil-fmt` covers these files too.
sigil fmt --check policies
```

`bun test` runs the same test files through `@spechtlabs/sigil`, loaded the
way the service loads them, and checks that `alert_routing.sigil` and
`src/lib/embedded.ts` match their sources.

The request samples in `../requests` carry their expected outcomes in
`cases.json`, and the service's tests route each one through these policies,
so the samples the console, the test suites and the load test send can't
drift from what the policies decide.

## Adding a team

1. Add `teams/<team>/alerts.sigil` defining `<team>.alerts`. It must invoke
   `paging()` at the top level, with the team's own `page_after`, and should
   invoke `routing()` there too, with its `muted` alerts.
2. Add `teams/<team>/alerts_test.yaml` with a case for every decision and
   reason the policy can reach.
3. Add the team to the team directory, `src/lib/teams/teams.yaml`, or the
   file `ALERTROUTER_TEAMS_FILE` names, with its on-call target and channel.
   alertrouter loads one policy per team in the directory, so the team is
   served from the next start. Run `bun run embed` so the copy compiled into
   the app has the new policy too.
4. Label the team's alerting rules with `team: <team>`, and `severity` one of
   `critical`, `warning` or `info`.
